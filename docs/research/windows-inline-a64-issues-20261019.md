# ARM64 Inline Hook：当前故障定位及验收边界

日期：2026-10-19；分支：`benefit`；目标：《紫》4.0.0；保持原版 sys-botbase 2.5。

## 实机证据
来自用户的 `raid-20261019-130229-65400606.jsonl`：
- TitleID、版本与 Build ID 的 **8 字节前缀**匹配。
- `main+0xE32984` 原指令 `0xAA1503E8`；八个指令锚点全部匹配。
- `main+0x343FC90..0x3440000` 可读、长度 880B、全部为 0。
- 实机尚**没有**验证该区域的执行权限、Hook 命中或实际发奖存档。
- Windows 到普通 sys-botbase 的读写本身由用户确认可用，无须反复验证通信基础。

## 已定位的核心错误
原 `native/sv_remote_code_patch/stub.S` 在命中路径再次执行 `BL memcpy`，仅保护 `x29/x30`。它改变 `x0..x18` 中的调用者保存寄存器（及可能的 SIMD/状态），不保证被拦截点的原函数仍可安全继续。**原版 jump/stub 不得作为稳定实机安装器启用。**

本地使用 clang/LLVM 编译检查了一个独立的无子调用、现场保护的 ARM64 复制循环，离线产物恰为 880B，模板仍位于偏移 `+0xA0`，模式位于 `+0x90`。这仅是汇编与布局验证；没有实机运行。

**与原构建脚本不兼容的地方：** 原 `build_offline_plan.py` 将 `+0x48` 当作 memcpy BL 的可替换槽，把 `+0x54` 当作返回 B 槽。独立复核的不同布局在 `+0x48` 是正常指令，`+0x54` 也是正常指令，返回占位位置在 `+0x78`。因此，不能仅把汇编替换掉而沿用原脚本：否则会覆盖有效指令，生成损坏代码。任何更新必须配套校验完整结构和重定位边界。

## 已提交的安全控制模型

`RaidCrawler.Core/Structures/RemoteInlineHookLifecycle.cs` 是**不连接 Switch** 的确定性状态机，配套 `RaidCrawler.Tests/RemoteInlineHookLifecycleTests.cs`。

状态：`NotInstalled → Staged → InstalledDisarmed → Armed`，发生失败则 `RecoveryRequired`。

限制：
- 必须有实际可执行内存、原入口指令、目标版本及 payload 回读等证据，才允许标记为已分阶段准备。
- 不能在未确认安装的情况下声明启用。
- **Armed 状态拒绝模板更新和卸载**；必须停用并等待已经执行的回调消退。
- 异常后不可直接重试安装，需先读回确认恢复原入口。
- 所有状态与事件目前只是离线模型，不能用它来虚构实机执行证明。

## 后续真正阻断条件
1. 必须核实候选 880B 对应的实际内存权限（读取 880B 全零不等于 RX 可执行）。
2. 确认代码执行时寄存器/条件标志/栈与原函数等价；新汇编与重定位器及所有静态测试必须同步修改。
3. 现有普通 sys-botbase 缺少线程暂停、执行中调用计数或同步原语；`CallbacksQuiescentVerified` 不能通过“软件连接成功”推断。避免运行时反复改写当前 CPU 可能正在读取的 720B 模板。
4. 首次安装必须明确用户授权，先进行读取与校验，再进行可回滚的事务；恢复入口前后需重新确认进程身份。游戏退出或异常时需要不依赖旧 ASLR base 的重新识别与恢复策略。
5. 安装字节回读、Hook 执行、奖励列表变化、最终背包及存档是**四个不同验收点**；必须分别验证，不能把前一个当后一个。

## 当前进展与安全结论
Windows 构建及纯 C# 测试可以验证软件逻辑；没有 Switch 实机写入执行证据，故仍不得标记 `HOOK_INSTALLED`、`HOOK_HIT` 或 `REWARD_SAVED`。优先处理版本锁、函数 ABI 和并发生命周期，而不是盲目向生产游戏装载一个离线汇编成功的 Hook。
