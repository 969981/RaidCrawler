## 用户操作

- 主界面 **发送副本 Hook** → **默认奖励25种（自定义最多28）**：添加/删除/重排道具、修改中文名称、道具 ID、数量 1–999、恢复默认、保存。
- 另一个入口：旧 sys-botbase 方案 A 窗口中的 **默认25种×999（自定义28）**；不再打开旧20种候选 RAM 批量写入。
- 配置路径：`%LOCALAPPDATA%\RaidCrawler\host-reward-preset.json`。JSON schema `raidcrawler.host.reward-preset.v1`，`SubjectType=5`。未保存时使用内置25种。
- Hook 窗口的 **空间预检（不写入）**：从当前 Native N1 捕获的720B源/发送两段重建离线候选，判断是否能无损保留原版奖励。该测试不验证道具是否可装包或游戏是否实际发奖。
- 校验：1–28 行、ID 1–65535、数量1–999、禁止重复 ID、每个名称非空，配置字段严格检查。

## 容量与安全

`RaidPoint` 最多 **45条**，不删改原版任何奖励。默认25条要求原版占用 **至多20条**；28条要求原版占用 **至多17条**。若例如原版已有21条，默认25条必定全单拒绝，不能只删原版或偷偷减至24条。

**999仅是请求数量，实际到账受游戏的 Item SlotMaxNum、物品口袋规则、当前库存、资格过滤和保存逻辑影响。尤其 Gimmighoul Coin 属特殊材料口袋，不能推断同其他普通物品共用上限。**

默认发奖资格：`subject=5`；非持有晶耀护符的参与者不会因设置这个列表而自动获得奖励。Native N1/N2 硬件验证仍待完成，且官方互联网多人模式不等同于本地 LDN 证据。

## 技术实现

- `RaidCrawler.Core/Host/HostRewardPreset.cs`：默认表、JSON、验证、25→28 自定义；调用 `BootstrapSendCopyPlanner` 完成完整明文离线规划。
- `RaidCrawler.WinForms/SubForms/HostRewardPresetWindow.cs`：设置管理，只有本机文件写入，不写 Switch。
- `RaidCrawler.Tests/Host/HostRewardPresetTests.cs`：默认顺序、JSON、上限、45槽容量、无损区、错误拒绝。

**待做的真正实机多行 Hook** 是另一个阶段：需要 C#→Native 多行请求协议、与运行态同局配置绑定、Native 校验和单次原子（全有或全无）追加，以及有护符参与者战后到账/保存的实测。现有 `RCHMB02` 邮箱只接受 1 条请求，不能将一个可编辑预设误写成已支持28条发送。
